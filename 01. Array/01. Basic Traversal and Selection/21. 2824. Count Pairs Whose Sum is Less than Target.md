# 21. 2824. Count Pairs Whose Sum is Less than Target

| Difficulty | Pattern | Source | Time | Space |
|:---:|:---:|:---:|:---:|:---:|
| **Easy** | Basic Traversal and Selection | [2824. Count Pairs Whose Sum is Less than Target](https://leetcode.com/problems/count-pairs-whose-sum-is-less-than-target/) | `O(n log n)` | `O(n)` |

## 1. Problem Statement

You get an integer array `nums` of length `n` and an integer `target`.

Return the number of pairs `(i, j)` with `0 <= i < j < n` and `nums[i] + nums[j] < target`.

### Example

```text
nums = [-1, 1, 2, 3, 1], target = 2

index:  0   1   2   3   4
nums:  -1   1   2   3   1

Good pairs:
(0, 1): -1 + 1 = 0 < 2
(0, 2): -1 + 2 = 1 < 2
(0, 4): -1 + 1 = 0 < 2

(0, 3): -1 + 3 = 2, not less than 2
All other pairs have sum 2 or more.

Output: 3
```

We use this same example in every section below.

### Constraints

- `1 <= nums.length == n <= 50`
- `-50 <= nums[i], target <= 50`

## 2. Core Theory

### What the problem really asks

Count pairs of **different positions** whose values add up to less than `target`.

### Why we are allowed to sort

The rule `i < j` only says "each pair once, no element with itself". It does not care about the order of values. If we shuffle the array, the set of value pairs stays the same. So the count stays the same.

### Why sorting helps

After sorting, put one pointer `l` at the left (smallest) and one pointer `r` at the right (biggest).

```text
sorted: [-1][ 1][ 1][ 2][ 3]
          l              r
```

- If `nums[l] + nums[r] < target`: then `nums[l]` plus **anything between l and r** is also small enough, because those values are `<= nums[r]`. That is `r - l` pairs at once. Then move `l` right.
- Otherwise the sum is too big. `nums[r]` is too big for `l`, and for every bigger left value too. So move `r` left.

Every step moves one pointer, so it is at most `n` steps after sorting.

## 3. Edge Cases

| Case | Input | Expected | Why it matters |
|:---|:---|:---:|:---|
| One element | `[5], target = 10` | `0` | No pairs |
| Sum equals target | `[1, 1], target = 2` | `0` | Must be strictly less |
| All pairs good | `[0, 0, 0], target = 1` | `3` | `3 · 2 / 2 = 3` pairs |
| Negative numbers | `[-5, -5], target = -9` | `1` | `-10 < -9`. Sorting and the logic work with negatives |
| Duplicates | `[1, 1, 1], target = 3` | `3` | Same values at different indices are different pairs |

## 4. Brute Force: Check Every Pair

### Idea

Two loops over `i < j`. Count if the sum is less than `target`.

### Code

```python
# Import List for type hints
from typing import List


# Check all pairs i < j
class SolutionBrute:

    # Main method
    def countPairs(self, nums: List[int], target: int) -> int:

        # Number of elements
        n = len(nums)

        # Number of good pairs
        count = 0

        # Pick the first index
        for i in range(n):

            # Pick a second index after it
            for j in range(i + 1, n):

                # Is the sum small enough?
                if nums[i] + nums[j] < target:

                    # Count this pair
                    count += 1

        # Return the total
        return count
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n²)` | All `n(n-1)/2` pairs |
| **Space** | `O(1)` | Only a counter |

With `n <= 50`, this is already fast enough. The two-pointer version is what interviewers want to see next.

## 5. Optimal Approach: Sort + Two Pointers

### Idea

1. Sort `nums`.
2. `l = 0`, `r = n - 1`, `count = 0`.
3. While `l < r`:
   - If `nums[l] + nums[r] < target`: `count += r - l`, then `l += 1`.
   - Else: `r -= 1`.
4. Return `count`.

### Visual Walkthrough (Story Version)

**The story:** 5 kids want to ride a seesaw in pairs. The seesaw breaks at weight `2` or more, so each pair must weigh **less than 2** together. The kids first line up from lightest to heaviest. A helper stands at each end of the line: Lefty at the lightest kid, Righty at the heaviest.

- If Lefty's kid + Righty's kid is safe, then Lefty's kid is safe with **every kid from Lefty up to Righty** (they are all lighter than Righty's kid). Count them all, then Lefty moves right.
- If it is not safe, Righty's kid is too heavy for anyone still left. Righty moves left.

### Code

```python
# Import List for type hints
from typing import List


# Solution for 2824. Count Pairs Whose Sum is Less than Target
class Solution:

    # Main method
    def countPairs(self, nums: List[int], target: int) -> int:

        # Sort a copy so the input is not changed
        nums = sorted(nums)

        # Left pointer at the smallest value
        l = 0

        # Right pointer at the biggest value
        r = len(nums) - 1

        # Number of good pairs
        count = 0

        # Keep going while the pointers have not met
        while l < r:

            # The smallest left value with the biggest right value is small enough
            if nums[l] + nums[r] < target:

                # nums[l] works with every index from l+1 to r
                count += r - l

                # Done with this left value
                l += 1

            # The sum is too big
            else:

                # nums[r] is too big for every remaining left value
                r -= 1

        # Return the total
        return count
```

## 6. Common Mistakes

| Mistake | What goes wrong | Fix |
|:---|:---|:---|
| Using `<=` | Pairs with sum equal to `target` are counted | Strictly `<` |
| `count += 1` instead of `r - l` | Misses all pairs between `l` and `r` | When `nums[l] + nums[r]` is small, all `r - l` pairs work |
| `count += r - l + 1` | Counts `nums[l]` with itself | Partners are `l+1..r`, that is `r - l` of them |
| Two pointers without sorting | The "everything between is smaller" idea is false | Sort first |
| `while l <= r` | Pairs an element with itself | Use `l < r` |

## 7. Interview Follow-ups

### Q1. Why is it fine to sort when the problem says `i < j`?

**Answer:**
- `i < j` only means "each pair of positions once".
- Sorting moves values but keeps the same set of pairs.
- So the number of good pairs does not change.

### Q2. Why can we add `r - l` at once?

**Answer:**
- The array is sorted, so every value between `l + 1` and `r` is at most `nums[r]`.
- If `nums[l] + nums[r]` is less than target, `nums[l]` plus any of them is too.
- That is `r - l` partners.

### Q3. Can we do it with binary search instead?

**Answer:**
- Yes. After sorting, for each `i`, binary search the last `j > i` with `nums[i] + nums[j] < target`.
- Add `j - i`. Total `O(n log n)`.

### Q4. Values are tiny (`-50..50`). Can we beat sorting?

**Answer:**
- Yes. Count how many times each value appears (101 buckets).
- Then add up counts for every value pair with sum below target, taking care of same-value pairs.
- That is `O(n + 101²)`, which is basically `O(n)`.

### Q5. What about "sum greater than target" or "sum in a range"?

**Answer:**
- Greater than target: total pairs minus pairs with sum `<= target`.
- Range `[lo, hi]`: count `< hi + 1` minus count `< lo`. Same two-pointer function twice.

## 8. Interview Explanation

> I need the number of index pairs with sum less than target. Brute force checks all pairs in O(n²). Since the count does not depend on order, I sort and use two pointers at both ends. If nums[l] + nums[r] is less than target, then nums[l] works with every element from l + 1 to r, because they are all no bigger than nums[r], so I add r - l and move l right. Otherwise nums[r] is too big for any remaining left value, so I move r left. Sorting is O(n log n) and the scan is O(n).
