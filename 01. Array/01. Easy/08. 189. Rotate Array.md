## 1. Problem Statement

Given an integer array `nums`, rotate the array to the right by `k` steps, where `k` is non-negative.

### Examples

```text
Example 1:

Input: nums = [1,2,3,4,5,6,7], k = 3
Output: [5,6,7,1,2,3,4]
Explanation:
rotate 1 steps to the right: [7,1,2,3,4,5,6]
rotate 2 steps to the right: [6,7,1,2,3,4,5]
rotate 3 steps to the right: [5,6,7,1,2,3,4]
```

```text
Example 2:

Input: nums = [-1,-100,3,99], k = 2
Output: [3,99,-1,-100]
Explanation:
rotate 1 steps to the right: [99,-1,-100,3]
rotate 2 steps to the right: [3,99,-1,-100]
```

### Constraints

- `1 <= nums.length <= 10^5`
- `-2^31 <= nums[i] <= 2^31 - 1`
- `0 <= k <= 10^5`

### Follow up

- Try to come up with as many solutions as you can. There are at least **three** different ways to solve this problem.
- Could you do it in-place with `O(1)` extra space?

### Example

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
```

Rotate one step:

```text
[7, 1, 2, 3, 4, 5, 6]
```

Rotate two steps:

```text
[6, 7, 1, 2, 3, 4, 5]
```

Rotate three steps:

```text
[5, 6, 7, 1, 2, 3, 4]
```

Final answer:

```text
[5, 6, 7, 1, 2, 3, 4]
```

## 2. Core Theory

A rotation is a **block swap**. If you split the array into two blocks `A` (the first `n-k` elements) and `B` (the last `k`), then rotating right by `k` is nothing more than turning `AB` into `BA`. Every approach on this page is a different way of performing that one swap — the naive one does it by repeated single shifts, the extra-array one by computing each element's destination directly, and the optimal one by exploiting a property of reversal.

The prerequisite fact is this identity, which holds for any two blocks:

```text
reverse(AB) == reverse(B) reverse(A)
```

Reversing a concatenation reverses each block *and* swaps their order. The block order is now what we want, but each block is individually backwards. So reverse each block again in place, and the two `reverse` operations cancel:

```text
start                A            B           [1 2 3 4][5 6 7]
step 1: reverse all  reverse(B)   reverse(A)  [7 6 5][4 3 2 1]
step 2: reverse [0,k) B            reverse(A)  [5 6 7][4 3 2 1]
step 3: reverse [k,n) B            A           [5 6 7][1 2 3 4]
```

Each element is touched by at most two swaps, so the whole thing is `O(n)` time with `O(1)` space — the answer to the follow-up.

**Why `k %= n` is mandatory, not cosmetic.** Rotating by `n` returns the array to itself, so rotation depth is only meaningful modulo `n`. The group of rotations on `n` elements is cyclic of order `n`. Skip the reduction and `reverse(0, k - 1)` is handed an out-of-range right index when `k > n`; worse, `k == n` makes step 2 reverse the whole array and step 3 a no-op, leaving the array reversed rather than rotated.

| Approach | Time | Space | Mechanism |
|:---|:---:|:---:|:---|
| Repeated single shift | `O(n * k)` | `O(1)` | Apply a 1-step rotation `k` times |
| Extra array | `O(n)` | `O(n)` | Write each element straight to `(i + k) % n` |
| Slicing | `O(n)` | `O(n)` | `B + A` built as a new list |
| Triple reversal | `O(n)` | `O(1)` | `AB -> reverse -> BA` |
| Cyclic replacement | `O(n)` | `O(1)` | Follow permutation cycles, carrying one temp |

**How to recognize this pattern.** Triple reversal is the tool whenever you must reorder two adjacent blocks in place with no extra memory — rotating a string, moving a suffix to the front, or in-place `std::rotate`. The giveaway is "swap two contiguous regions" plus an `O(1)` space constraint. The cyclic-replacement alternative is worth knowing because it generalises to *any* in-place permutation, not just rotations; its subtlety is that a rotation by `k` decomposes into exactly `gcd(n, k)` disjoint cycles, which is why a single cycle walk is not enough and a `count` guard is needed.

## 3. Core Intuition

For right rotation by k, the last k elements should come to the front.

Example:

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
```

Break array into two parts:

```text
First part: [1, 2, 3, 4]
Last k part: [5, 6, 7]
```

After rotation:

```text
[5, 6, 7] + [1, 2, 3, 4]
```

Result:

```text
[5, 6, 7, 1, 2, 3, 4]
```

## 4. Important Point: Why `k = k % n`?

Suppose:

```text
nums = [1, 2, 3, 4, 5]
n = 5
k = 5
```

Rotating 5 times gives the same array.

```text
[1, 2, 3, 4, 5]
```

So rotation by n steps changes nothing.

Therefore:

```text
k = k % n
```

Example:

```text
nums = [1, 2, 3, 4, 5]
k = 7
```

Since array length is 5:

```text
k = 7 % 5 = 2
```

So rotating by 7 steps is same as rotating by 2 steps.

## 5. Edge Cases

| Case | Input | Expected | Why it matters |
|:---|:---|:---:|:---|
| `k == 0` | `nums=[1,2,3], k=0` | `[1,2,3]` | No rotation. Triple reversal must still be a no-op: `reverse(0,-1)` and `reverse(0,2)` after a full reverse cancel correctly. |
| `k == n` | `nums=[1,2,3], k=3` | `[1,2,3]` | `k %= n` makes this `k = 0`. Without the reduction, step 2 reverses everything and step 3 does nothing, leaving `[3,2,1]`. |
| `k > n` | `nums=[1,2,3,4,5], k=7` | `[4,5,1,2,3]` | `7 % 5 = 2`. Without `k %= n`, `reverse(0, 6)` indexes past the end or silently misbehaves. |
| `k` a huge multiple of `n` | `nums=[1,2], k=100000` | `[1,2]` | `100000 % 2 == 0`. Confirms the modulo, not a loop, bounds the work — the brute force would do `10^5` passes. |
| Single element | `nums=[1], k=1` | `[1]` | `n == 1`, so `k %= 1` is always `0`. Also the case where `k % n` guards a division by the array length. |
| Two elements | `nums=[1,2], k=1` | `[2,1]` | Smallest genuine rotation; catches off-by-one in the `reverse(0, k-1)` / `reverse(k, n-1)` split. |
| All identical elements | `nums=[7,7,7], k=2` | `[7,7,7]` | Output is indistinguishable from the input, so only an index-level bug (an exception) shows — useful as a crash test. |
| Negative values | `nums=[-1,-100,3,99], k=2` | `[3,99,-1,-100]` | Values are opaque payloads; nothing in the algorithm may depend on sign or magnitude. |
| Duplicates present | `nums=[1,2,1,2], k=2` | `[1,2,1,2]` | Duplicates must not confuse cyclic replacement, which tracks *positions*, never values. |
| Already-satisfied rotation | `nums=[1,1,1,1], k=3` | `[1,1,1,1]` | The work still happens; correctness must not rely on detecting a shortcut. |
| Left rotation by `k` | `nums=[1,2,3,4,5], k=2` left | `[3,4,5,1,2]` | A common interviewer twist: left-rotate by `k` equals right-rotate by `n - k`. |

## 6. Brute Force Solution

### Intuition

Rotate the array one step at a time.

For every single right rotation:

```text
Take the last element
Move every element one step right
Put last element at index 0
```

### Brute Force Dry Run

```text
nums = [1, 2, 3, 4, 5]
k = 2
```

**First rotation**

Last element:

```text
5
```

Shift remaining elements right:

```text
[1, 1, 2, 3, 4]
```

Put 5 at front:

```text
[5, 1, 2, 3, 4]
```

**Second rotation**

Last element:

```text
4
```

Shift remaining elements right:

```text
[5, 5, 1, 2, 3]
```

Put 4 at front:

```text
[4, 5, 1, 2, 3]
```

Final answer:

```text
[4, 5, 1, 2, 3]
```

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def rotate(self, nums: List[int], k: int) -> None:

        # Store the length of the array
        n = len(nums)

        # Reduce k because rotating n times gives the same array
        k = k % n

        # Perform one-step rotation k times
        for _ in range(k):

            # Store the last element because it will move to the front
            last_element = nums[n - 1]

            # Move every element one position to the right
            for i in range(n - 1, 0, -1):

                # Copy previous element to current position
                nums[i] = nums[i - 1]

            # Put the old last element at the first position
            nums[0] = last_element
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n * k)` | Because for each of the k rotations, we shift n elements. |
| **Space** | `O(1)` | Because we only use one extra variable. |

## 7. Better Solution: Use Extra Array

### Intuition

Instead of rotating one by one, directly place every element at its final position.

For right rotation by k:

```text
Element at index i moves to index (i + k) % n
```

### Why `(i + k) % n`?

Example:

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
```

Element 1 at index 0 should move to index:

```text
(0 + 3) % 7 = 3
```

Element 5 at index 4 should move to index:

```text
(4 + 3) % 7 = 0
```

So 5 wraps around and comes to the front.

### Dry Run

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
n = 7
```

Mapping:

| Element | Old Index | New Index `(i + k) % n` |
|:---:|:---:|:---:|
| 1 | 0 | 3 |
| 2 | 1 | 4 |
| 3 | 2 | 5 |
| 4 | 3 | 6 |
| 5 | 4 | 0 |
| 6 | 5 | 1 |
| 7 | 6 | 2 |

Final:

```text
[5, 6, 7, 1, 2, 3, 4]
```

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def rotate(self, nums: List[int], k: int) -> None:

        # Store the length of the array
        n = len(nums)

        # Reduce k because rotating n times gives the same array
        k = k % n

        # Create a temporary array of same size
        rotated = [0] * n

        # Traverse every element of original array
        for i in range(n):

            # Calculate new position after right rotation
            new_index = (i + k) % n

            # Place current element at its final rotated position
            rotated[new_index] = nums[i]

        # Copy rotated values back into nums because problem needs in-place modification
        for i in range(n):

            # Update original array
            nums[i] = rotated[i]
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because we traverse the array twice. |
| **Space** | `O(n)` | Because we use an extra array. |

## 8. Better Pythonic Solution: Slicing

### Intuition

For right rotation by k, take the last k elements and put them before the remaining elements.

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
```

Last k elements:

```text
[5, 6, 7]
```

Remaining elements:

```text
[1, 2, 3, 4]
```

Final:

```text
[5, 6, 7, 1, 2, 3, 4]
```

### Slicing Code

```python
from typing import List

class Solution:
    def rotate(self, nums: List[int], k: int) -> None:
        # Store the length of the array
        n = len(nums)

        # Reduce k because k can be greater than n
        k = k % n

        # Replace nums content with last k elements followed by first n-k elements
        nums[:] = nums[n - k:] + nums[:n - k]
```

### Slicing Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because slicing walks the whole array. |
| **Space** | `O(n)` | Even though it looks very small, slicing creates new lists internally. |

This is accepted, but it is not the best for the follow-up asking `O(1)` extra space.

## 9. Most Optimal Solution: Reverse Method

### Core Intuition

We want:

```text
nums = [1, 2, 3, 4, 5, 6, 7]
k = 3
```

Final answer should be:

```text
[5, 6, 7, 1, 2, 3, 4]
```

Think of the array as two parts:

```text
A = [1, 2, 3, 4]
B = [5, 6, 7]
```

Original:

```text
A B
```

After right rotation:

```text
B A
```

So we need to convert:

```text
A B  ->  B A
```

We can do that using three reversals.

### Three Reversal Trick

Original:

```text
[1, 2, 3, 4, 5, 6, 7]
```

Step 1: Reverse the whole array

```text
[7, 6, 5, 4, 3, 2, 1]
```

Step 2: Reverse first k elements

```text
[5, 6, 7, 4, 3, 2, 1]
```

Step 3: Reverse remaining n-k elements

```text
[5, 6, 7, 1, 2, 3, 4]
```

Done.

## 10. Why Reverse Method Works

Original array:

```text
A B
```

Where:

```text
A = first n-k elements
B = last k elements
```

We want:

```text
B A
```

Now reverse the whole array:

```text
reverse(A B) = reverse(B) reverse(A)
```

Then reverse first k elements:

```text
B reverse(A)
```

Then reverse remaining part:

```text
B A
```

That is exactly the rotated array.




**Reverse remaining elements**

Reverse indices 3 to 6:

```text

```

After reversing:

```text

```

Final answer:

```text
[5, 6, 7, 1, 2, 3, 4]
```

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def rotate(self, nums: List[int], k: int) -> None:

        # Store the length of the array
        n = len(nums)

        # Reduce k because rotating n times gives the same array
        k = k % n

        # Helper function to reverse part of the array in-place
        def reverse(left: int, right: int) -> None:

            # Continue until both pointers meet or cross
            while left < right:

                # Swap left and right elements
                nums[left], nums[right] = nums[right], nums[left]

                # Move left pointer forward
                left += 1

                # Move right pointer backward
                right -= 1

        # Step 1: Reverse the whole array
        reverse(0, n - 1)

        # Step 2: Reverse the first k elements
        reverse(0, k - 1)

        # Step 3: Reverse the remaining n-k elements
        reverse(k, n - 1)
```

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because each element is involved in a constant number of swaps. |
| **Space** | `O(1)` | Because we rotate the array in-place. |

## 13. Common Mistakes

| Mistake | Why it breaks | Fix |
|:---|:---|:---|
| Forgetting `k %= n` | With `k > n` the reversal bounds walk off the array, and with `k == n` step 2 reverses the whole array while step 3 is a no-op, leaving the array reversed instead of unchanged. | Do `k = k % n` as the very first statement after computing `n`. |
| Rotating left instead of right | Reversing the first `n-k` and last `k` blocks (rather than the first `k` and last `n-k`) produces a left rotation. `[1,2,3,4,5,6,7]` with `k=3` yields `[4,5,6,7,1,2,3]`. | Right rotation is `reverse(0, n-1)`, then `reverse(0, k-1)`, then `reverse(k, n-1)`. For a left rotation by `k`, call the same routine with `n - k`. |
| Writing `nums = nums[n-k:] + nums[:n-k]` | This rebinds the local name to a new list; the caller's array is untouched, so an in-place-mutation grader sees no change at all. | Use slice assignment `nums[:] = ...`, which writes through to the same object. |
| Doing `k %= n` when `n` could be `0` | `ZeroDivisionError` (or a modulo-by-zero crash in C++/Java) on an empty array. LeetCode's constraints forbid it, but a rewritten or library version hits it. | Guard with `if n == 0: return` before the modulo, or use `k % n if n else 0`. |
| Cyclic replacement with a single cycle walk and no `count` | A rotation by `k` splits into `gcd(n, k)` disjoint cycles. `nums=[1,2,3,4,5,6], k=2` has `gcd=2`, so one walk covers only half the elements and the rest keep their original values. | Track `count` of placed elements and advance `start` until `count == n`. |
| Overwriting before saving in cyclic replacement | Assigning `nums[next_index] = previous_value` without first stashing the old `nums[next_index]` destroys a value that has not been relocated yet. | Save `temp = nums[next_index]` *before* the write, then set `previous_value = temp`. |

## 14. Another Optimal Solution: Cyclic Replacement

This is also `O(n)` time and `O(1)` space, but it is slightly harder than reverse method.

### Intuition

Each element has a final position:

```text
new_index = (current_index + k) % n
```

So we can move elements directly to their final position.

But if we directly overwrite values, we may lose data.

Therefore, we keep one value in a temporary variable and keep moving elements in cycles.

### Example

```text
nums = [1, 2, 3, 4, 5, 6]
k = 2
```

Index mapping:

```text
0 -> 2
2 -> 4
4 -> 0
```

This is one cycle.

Another cycle:

```text
1 -> 3
3 -> 5
5 -> 1
```

So sometimes one cycle does not cover all elements.

That is why we keep a count variable until all n elements are moved.

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def rotate(self, nums: List[int], k: int) -> None:

        # Store the length of the array
        n = len(nums)

        # Reduce k because rotating n times gives same array
        k = k % n

        # Count how many elements have been moved
        count = 0

        # Start cycles from index 0, 1, 2, ...
        start = 0

        # Continue until every element is placed correctly
        while count < n:

            # Current index starts from cycle start
            current = start

            # Store the value that needs to be moved
            previous_value = nums[start]

            # Keep moving inside the current cycle
            while True:

                # Find the next index where previous_value should go
                next_index = (current + k) % n

                # Store the value at next_index before overwriting it
                temp = nums[next_index]

                # Place previous_value at its correct next position
                nums[next_index] = previous_value

                # The overwritten value now needs to be moved next
                previous_value = temp

                # Move current pointer to next_index
                current = next_index

                # One element has been placed correctly
                count += 1

                # If we returned to the start, this cycle is complete
                if current == start:
                    break

            # Move to next possible cycle start
            start += 1
```

### Cyclic Replacement Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because every element is moved exactly once. |
| **Space** | `O(1)` | Because we only use a few temporary variables. |

But in interviews, the **reverse method** is usually easier to explain and safer to implement.

## 15. Interview Follow-ups

**Q: What if `k` is astronomically large — say `10^18`, beyond a 32-bit int?**

A: It changes nothing, because `k %= n` collapses any `k` into `[0, n)` in a single modulo. That is the whole point of the reduction: the cost of the rotation depends on `n`, never on `k`. The only practical concern is the *type* of `k`: read it into a 64-bit integer (Python is arbitrary precision, so this is free) and take the modulo before any arithmetic that could overflow. Contrast this with the brute-force shift-one-at-a-time approach, which would attempt `10^18` passes — the modulo is what makes large `k` a non-issue.

**Q: Rotate left by `k` instead of right. How much of your code changes?**

A: One line. A left rotation by `k` is exactly a right rotation by `n - k`, since shifting the window forward by `k` is the same as shifting it backward by `n - k` on a cycle. So do `k = k % n` and then `k = n - k` before calling the same triple-reversal routine (guard `k = 0` separately, since `n - 0 == n`, which must reduce back to `0`). Alternatively, keep the same three reversals but swap the split point: reverse all, then `reverse(0, n-k-1)`, then `reverse(n-k, n-1)`.

**Q: Can you do it in `O(1)` space *without* reversal?**

A: Yes — cyclic replacement, which is on this page. Each element at index `i` belongs at `(i + k) % n`, so you pick up one value in a temp variable, drop it at its destination, pick up whatever was there, and continue. The catch is that this traverses a permutation cycle, and a rotation by `k` decomposes into exactly `gcd(n, k)` disjoint cycles — so you need an outer loop over starting offsets plus a `count` of placed elements. Same `O(n)` time and `O(1)` space, but with worse cache locality than reversal (it jumps by `k` each step rather than scanning linearly) and far more room for off-by-one bugs. In an interview I would state it exists and then implement the reversal.

**Q: What if the data is a singly linked list rather than an array?**

A: The reversal trick is awkward on a singly linked list, so use the structural shortcut instead. Walk the list to find its length `n` and its tail, reduce `k %= n`, then close the list into a ring by pointing `tail.next` at `head`. Now walk `n - k` steps from the old head; that node is the new tail, its `next` is the new head, and you cut there by setting `new_tail.next = None`. That is `O(n)` time, `O(1)` space, and a single pass plus a partial one — this is LeetCode 61.

**Q: The array is far too large for memory and lives on disk. What now?**

A: Reversal is exactly the right primitive here, because all three of its passes are **sequential** scans. Reversing a block on disk means streaming from both ends toward the middle, swapping as you go, which is friendly to block-based I/O and needs only a couple of buffered pages resident. Cyclic replacement, by contrast, jumps by `k` on every step and would fault a page per element. So the triple reversal costs three sequential passes over the file, `O(n / B)` I/Os for block size `B`, whereas the naive approach is catastrophic.

## 16. Interview Explanation

> For right rotation by `k`, the last `k` elements should come to the front. First I reduce `k` using `k = k % n`, because rotating by `n` steps gives the same array. The brute force is to rotate one step at a time, which is `O(n * k)`. A better way is to use an extra array and place each element at index `(i + k) % n`, which is `O(n)` time but `O(n)` space. The most optimal way is the reverse method: think of the array as `A B`, where `A` is the first `n-k` elements and `B` is the last `k` elements. We want `B A`. Reversing the whole array gives `reverse(B) reverse(A)`, then reversing the first `k` elements gives `B reverse(A)`, and reversing the remaining part gives `B A`, which is exactly the rotated array. This runs in `O(n)` time and `O(1)` space. There is also a cyclic replacement approach with the same complexity, but the reverse method is easier to explain and safer to implement.

```python
def rotate(nums, k):

            # Move right pointer backward

    # Step 1: Reverse the whole array
    reverse(0, n - 1)

    # Step 2: Reverse the first k elements
    reverse(0, k - 1)

    # Step 3: Reverse the remaining n-k elements
    reverse(k, n - 1)

    # Return the rotated array
    return nums

arr = [1, 2, 3, 4, 5, 6, 7]
rotate(arr, 3)
assert arr == [5, 6, 7, 1, 2, 3, 4]

arr = [-1, -100, 3, 99]
rotate(arr, 2)
assert arr == [3, 99, -1, -100]

# k == 0: no rotation.
arr = [1, 2, 3]
rotate(arr, 0)
assert arr == [1, 2, 3]

# k == n: k %= n makes this k = 0, so the array must come back unchanged.
arr = [1, 2, 3]
rotate(arr, 3)
assert arr == [1, 2, 3]

# k > n: 7 % 5 = 2, must reduce via k %= n.
arr = [1, 2, 3, 4, 5]
rotate(arr, 7)
assert arr == [4, 5, 1, 2, 3]

# k a huge multiple of n: 100000 % 2 == 0, confirms modulo bounds the work, not a loop.
arr = [1, 2]
rotate(arr, 100000)
assert arr == [1, 2]
arr = [1, 2, 3]
rotate(arr, 10 ** 18 + 1)
assert arr == [2, 3, 1]

# Single element: n == 1, so k %= 1 is always 0.
arr = [1]
rotate(arr, 1)
assert arr == [1]

# Two elements: smallest genuine rotation, catches off-by-one in the reverse split.
arr = [1, 2]
rotate(arr, 1)
assert arr == [2, 1]

# All identical elements: output looks unchanged, so this is really a crash/index test.
arr = [7, 7, 7]
rotate(arr, 2)
assert arr == [7, 7, 7]

# Duplicates present: cyclic/positional logic must not get confused by repeated values.
arr = [1, 2, 1, 2]
rotate(arr, 2)
assert arr == [1, 2, 1, 2]

# Empty input is handled without a modulo-by-zero.
arr = []
rotate(arr, 3)
assert arr == []

# Left rotation by k equals a right rotation by n - k.
arr = [1, 2, 3, 4, 5]
rotate(arr, len(arr) - 2)
assert arr == [3, 4, 5, 1, 2]

import random

    # Copy the base array so rotate() can mutate it in place
    got = list(base)

    rotate(got, k)

    # Compute the effective shift
    shift = k % n

    # Compute the expected result using slicing
    expected = base[n - shift:] + base[:n - shift]

    # Compare the rotated copy against the expected slice-based result
    assert got == expected, (base, k, got, expected)
```
