| Difficulty | Pattern | Source | Time | Space |

## 1. Problem Statement

You are given two integer arrays `nums1` and `nums2`, sorted in **non-decreasing order**, and two integers `m` and `n`, representing the number of elements in `nums1` and `nums2` respectively.

**Merge** `nums1` and `nums2` into a single array sorted in **non-decreasing order**.

The final sorted array should not be returned by the function, but instead be *stored inside the array* `nums1`. To accommodate this, `nums1` has a length of `m + n`, where the first `m` elements denote the elements that should be merged, and the last `n` elements are set to `0` and should be ignored. `nums2` has a length of `n`.

### Examples

```text
Example 1:

Input: nums1 = [1,2,3,0,0,0], m = 3, nums2 = [2,5,6], n = 3
Output: [1,2,2,3,5,6]
Explanation: The arrays we are merging are [1,2,3] and [2,5,6].
The result of the merge is [1,2,2,3,5,6] with the underlined elements coming from nums1.
```

```text
Example 2:

Input: nums1 = [1], m = 1, nums2 = [], n = 0
Output: [1]
Explanation: The arrays we are merging are [1] and [].
The result of the merge is [1].
```

```text
Example 3:

Input: nums1 = [0], m = 0, nums2 = [1], n = 1
Output: [1]
Explanation: The arrays we are merging are [] and [1].
The result of the merge is [1].
Note that because m = 0, there are no elements in nums1. The 0 is only there to ensure the
merge result can fit in nums1.
```

### Constraints

- `nums1.length == m + n`
- `nums2.length == n`
- `0 <= m, n <= 200`
- `1 <= m + n <= 200`
- `-10^9 <= nums1[i], nums2[j] <= 10^9`

### Follow up

Can you come up with an algorithm that runs in `O(m + n)` time?

## 2. Core Theory

The general technique is the **merge of two sorted sequences** — the combining half of merge sort, and the foundation of every k-way merge, external sort, and sorted-list intersection you will ever write. The insight it exploits is small but powerful: if two sequences are each sorted, then the overall smallest remaining element is always at the head of one of them. You never have to search. Comparing the two heads and taking the winner produces the next output element in `O(1)`, so the whole merge costs `O(m + n)` — one comparison per element emitted, and each element emitted exactly once.

Symmetrically, the overall **largest** remaining element is always at the *tail* of one of them. That symmetry is what makes this particular problem solvable in place, and it is the prerequisite idea worth internalising.

**Why filling from the back is safe.** The danger with an in-place merge is overwriting a value in `nums1` before you have consumed it. Merging forward does exactly that: writing the merged result to `nums1[0]` clobbers a real element while `i` still needs to read it. Merging backward cannot, and the reason is a counting argument rather than luck.

Let `k` be the write index and `i` the read index into `nums1`. Initially `k = m + n - 1` and `i = m - 1`, so `k - i = n >= 0`. Every step advances `k` by one, but advances `i` only when the value came from `nums1`; when it came from `nums2`, `i` does not move at all. So `k` falls at least as fast as `i`, and the gap `k - i` never becomes negative:

```text
                   i (read)              k (write)
nums1 = [ 1, 2, 3, |, 0, 0, 0 ]              |
                   ^                          ^
          k - i = n = 3  ->  write pointer is always at or ahead of read pointer
```

The invariant is therefore **`k >= i` at all times**. When `k > i`, the write lands in the free tail or on an already-consumed slot. When `k == i`, the write is `nums1[i] = nums1[i]`, a harmless self-assignment — and this equality can only occur once `nums2` is exhausted, at which point the remaining prefix of `nums1` is already in its final position.

That last fact explains the asymmetric cleanup loop. If `nums1` runs out first, leftover `nums2` values must still be copied down. If `nums2` runs out first, the leftover `nums1` values are already sitting exactly where they belong, so there is nothing to do.

| Direction | Space | Safe in place? | Why |
|:---|:---:|:---:|:---|
| Front to back | `O(m + n)` | No | Writing to `nums1[0]` destroys unread data |
| Back to front | `O(1)` | Yes | Free space is at the back; `k >= i` always holds |

**How to recognize this pattern.** Two signals together: the inputs are already sorted (so a comparison-based `O(n log n)` sort is wasteful), and the destination buffer has slack at one end. Whenever the free space sits at the back, fill from the back. This same reversed-fill trick applies to in-place string manipulations, array compaction with growth, and merging linked lists into a pre-sized array. When there is no slack at all, a true in-place merge needs the much harder `O((m+n) log(m+n))` block-swap or gap-based algorithms.

| All identical elements | `nums1=[2,2,0,0], m=2, nums2=[2,2], n=2` | `[2,2,2,2]` | Every comparison ties. A strict `>` sends every tie down the `nums2` branch, which must still terminate correctly. |
| Negative values | `nums1=[-3,-1,0,0], m=2, nums2=[-5,-2], n=2` | `[-5,-3,-2,-1]` | Placeholder `0`s are *larger* than real data here — proof that the algorithm must rely on `m` and `n`, never on spotting zeros. |
| Interleaved | `nums1=[1,3,5,0,0,0], m=3, nums2=[2,4,6], n=3` | `[1,2,3,4,5,6]` | Pointers alternate on every step; exercises both branches maximally. |
| Single element each | `nums1=[2,0], m=1, nums2=[1], n=1` | `[1,2]` | The smallest case where an element actually moves position. |
| Both empty | `nums1=[], m=0, nums2=[], n=0` | `[]` | Outside the constraints (`1 <= m + n`) but must not crash; all pointers start negative. |

## 5. Core Intuition

This is the same idea as the **merge step of merge sort**.

When two arrays are already sorted, we can merge them using two pointers.

Example:

```text
nums1 real part = [1, 2, 3]
nums2           = [2, 5, 6]
```

Compare smallest elements:

```text
1 and 2 -> pick 1
2 and 2 -> pick 2
3 and 2 -> pick 2
3 and 5 -> pick 3
then remaining 5, 6
```

Result:

```text
[1, 2, 2, 3, 5, 6]
```

## 6. Important Catch

The result must be stored inside `nums1`.

If we merge from the front directly, we may overwrite useful values in `nums1`.

Example:

```text
nums1 = [1, 2, 3, 0, 0, 0]
nums2 = [2, 5, 6]
```

If we write from index 0, we may destroy 1, 2, 3 before using them.

So the best trick is:

```text
Merge from the back.
```

Because the back side of `nums1` has empty space.

## 7. Brute Force Solution: Copy + Sort

### Intuition

Put all elements of `nums2` into the empty space of `nums1`.

Then sort `nums1`.

### Approach

1. Copy every element of `nums2` into `nums1` after index `m - 1`.
2. Sort `nums1`.

### Dry Run

```text
nums1 = [1, 2, 3, 0, 0, 0], m = 3
nums2 = [2, 5, 6], n = 3
```

Copy `nums2` into extra space:

```text
nums1 = [1, 2, 3, 2, 5, 6]
```

Sort:

```text
nums1 = [1, 2, 2, 3, 5, 6]
```

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def merge(self, nums1: List[int], m: int, nums2: List[int], n: int) -> None:

        # Start writing nums2 elements from index m in nums1
        index = m

        # Traverse every element of nums2
        for num in nums2:

            # Copy current nums2 element into nums1
            nums1[index] = num

            # Move index forward
            index += 1

        # Sort nums1 in-place
        nums1.sort()
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O((m + n) log(m + n))` | Because sorting the final array takes `O((m+n)log(m+n))`. |
| **Space** | `O(1)` or `O(m+n)` | Depending on sorting implementation. |

This is easy, but it does not use the fact that both arrays are already sorted.

## 8. Better Solution: Extra Array Merge

### Intuition

Use two pointers from the front.

One pointer reads `nums1`.

One pointer reads `nums2`.

Whichever value is smaller gets added to a temporary result array.

### Approach

Use:

```text
i = 0 for nums1
j = 0 for nums2
```

Compare:

```text
nums1[i] and nums2[j]
```

Add the smaller one into `merged`.

After one array finishes, add remaining elements from the other array.

Finally copy `merged` back to `nums1`.

### Dry Run

```text
nums1 real = [1, 2, 3]
nums2      = [2, 5, 6]
```

Initial:

```text
i = 0
j = 0
merged = []
```

| nums1[i] | nums2[j] | Pick | merged |
|:---:|:---:|:---:|:---:|
| 1 | 2 | 1 | [1] |
| 2 | 2 | 2 from nums1 | [1, 2] |
| 3 | 2 | 2 from nums2 | [1, 2, 2] |
| 3 | 5 | 3 | [1, 2, 2, 3] |

Now `nums1` real part is finished.

Add remaining `nums2`:

```text
[5, 6]
```

Final:

```text
merged = [1, 2, 2, 3, 5, 6]
```

Copy to `nums1`.

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def merge(self, nums1: List[int], m: int, nums2: List[int], n: int) -> None:

        # Pointer for valid elements of nums1
        i = 0

        # Pointer for nums2
        j = 0

        # Temporary array to store merged result
        merged = []

        # Merge while both arrays have elements left
        while i < m and j < n:

            # If nums1 current element is smaller or equal
            if nums1[i] <= nums2[j]:

                # Add nums1 element to merged array
                merged.append(nums1[i])

                # Move nums1 pointer forward
                i += 1

            # Otherwise nums2 current element is smaller
            else:

                # Add nums2 element to merged array
                merged.append(nums2[j])

                # Move nums2 pointer forward
                j += 1

        # Add remaining valid nums1 elements
        while i < m:

            # Append current nums1 element
            merged.append(nums1[i])

            # Move nums1 pointer
            i += 1

        # Add remaining nums2 elements
        while j < n:

            # Append current nums2 element
            merged.append(nums2[j])

            # Move nums2 pointer
            j += 1

        # Copy merged result back into nums1
        for index in range(m + n):

            # Update nums1 in-place
            nums1[index] = merged[index]
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(m + n)` | Because each element is processed once. |
| **Space** | `O(m + n)` | Because we use a temporary `merged` array. |

## 9. Most Optimal Solution: Merge From Back

### Core Intuition

`nums1` already has empty space at the end.

So instead of filling from the front, we fill from the back.

Why?

Because the largest elements should go to the end.

Example:

```text
nums1 = [1, 2, 3, 0, 0, 0]
nums2 = [2, 5, 6]
```

The biggest element among both arrays is 6.

It should go to the last position.

The next biggest is 5.

It should go to the second last position.

So we compare from the back and place the larger value at the end.

### Pointers Used

```text
i = m - 1
```

Points to last real element of `nums1`.

```text
j = n - 1
```

Points to last element of `nums2`.

```text
k = m + n - 1
```

Points to last position of `nums1`, where final value should be placed.

### Main Logic

Compare:

```text
nums1[i] and nums2[j]
```

The larger value goes to:

```text
nums1[k]
```

Then move the corresponding pointer backward.

## 11. Why We Only Need to Copy Remaining nums2

At the end, there are two possibilities.

### Case 1: nums2 still has elements

Example:

```text
nums1 = [4, 5, 6, 0, 0, 0]
nums2 = [1, 2, 3]
```

After placing bigger elements, some `nums2` elements may remain.

Those must be copied to the front.

### Case 2: nums1 still has elements

Example:

```text
nums1 = [1, 2, 3, 0, 0, 0]
nums2 = [4, 5, 6]
```

If `nums1` elements remain, they are already in their correct place.

No need to copy them.

That is why final loop only needs:

```text
while j >= 0:
    nums1[k] = nums2[j]
```

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def merge(self, nums1: List[int], m: int, nums2: List[int], n: int) -> None:

        # Pointer for the last valid element in nums1
        i = m - 1

        # Pointer for the last element in nums2
        j = n - 1

        # Pointer for the last position in nums1
        k = m + n - 1

        # Merge from the back while both arrays have elements left
        while i >= 0 and j >= 0:

            # If nums1 has the larger current element
            if nums1[i] > nums2[j]:

                # Put nums1's current element at the final position
                nums1[k] = nums1[i]

                # Move nums1 pointer backward
                i -= 1

            # If nums2 has the larger or equal current element
            else:

                # Put nums2's current element at the final position
                nums1[k] = nums2[j]

                # Move nums2 pointer backward
                j -= 1

            # Move final write pointer backward
            k -= 1

        # Copy remaining nums2 elements, if any
        while j >= 0:

            # Put remaining nums2 element into nums1
            nums1[k] = nums2[j]

            # Move nums2 pointer backward
            j -= 1

            # Move final write pointer backward
            k -= 1
```

## 13. Common Mistakes

| Mistake | Why it breaks | Fix |
|:---|:---|:---|
| Merging from the front instead of the back | Writing to `nums1[0]` overwrites a real element that `i` has not read yet, silently corrupting the result. `[1,2,3,0,0,0]` with `[2,5,6]` yields garbage. | Start at `k = m + n - 1` and fill backwards, where the free space is. |
| Omitting the trailing `while j >= 0` loop | When `m == 0`, or whenever `nums1` drains first, the leftover `nums2` values are never copied. `nums1=[0], m=0, nums2=[1]` returns `[0]` instead of `[1]`. | Always run the cleanup loop for `nums2` after the main loop. |
| Adding a symmetric `while i >= 0` cleanup loop | Harmless but pointless — leftover `nums1` elements are already in their final positions. It also invites an off-by-one that overwrites correct data. | Only `nums2` needs draining. Leftover `nums1` values need no work. |
| Using `len(nums1)` in place of `m` | `nums1` has length `m + n`, so the loop reads the trailing placeholder zeros as if they were real data and merges them into the output. | Bound the `nums1` read by `m`, which is the count of *real* elements. |
| Detecting the real region by scanning for zeros | `0` is a legal value and negatives make the placeholders the largest entries in the array. The real/placeholder split is only knowable from `m`. | Trust `m` and `n`; never inspect values to infer boundaries. |
| Initialising `k = m + n` instead of `m + n - 1` | The first write lands one past the end, raising `IndexError` (or corrupting memory in C++). | `k` is an index, so the last valid slot is `m + n - 1`. |
| Rebinding with `nums1 = merged` | Assigning a new list to the local name leaves the caller's array unchanged; the in-place grader sees nothing. | Write through the existing object with index assignment or `nums1[:] = merged`. |

## 14. Interview Follow-ups

**Q: What if `nums1` had no spare capacity — a true in-place merge of two adjacent sorted regions?**

A: This is genuinely hard, and admitting that is the right first move. With zero extra space the `O(m + n)` bound is lost; the known solutions are `O((m + n) log(m + n))`. The practical one is the *gap method* (a Shell-sort-style pass): start with a gap of `ceil((m+n)/2)`, compare and swap every pair of elements that distance apart across the combined array, then halve the gap and repeat until it reaches zero. It is `O(1)` space and reasonably simple to code. The theoretically optimal `O(m+n)`-time, `O(1)`-space in-place merge exists (Kronrod's block-rotation method) but is far too intricate for an interview.

**Q: Generalise it to merging `k` sorted arrays instead of two.**

A: The comparison step becomes the bottleneck — picking the smallest of `k` heads naively costs `O(k)` per element, giving `O(N k)` overall for `N` total elements. Replace the linear scan with a min-heap keyed on the head values, holding one entry per array. Pop the smallest, emit it, and push that array's next element. Each of the `N` elements costs one `O(log k)` heap operation, so the total is `O(N log k)` time with `O(k)` space. That is LeetCode 23 in linked-list form. An alternative is pairwise merging in a tournament, which gives the same `O(N log k)`.

**Q: The arrays are far too large to fit in memory. How do you merge them?**

A: This is the external merge sort scenario, and the merge step is what makes it work — it is inherently sequential, so it streams beautifully. Read both inputs through buffered readers, keep only the current head of each in memory, and write the winner to a buffered output. Memory usage is `O(B)` for block size `B`, independent of file size, and the I/O cost is one sequential pass over each file. This is exactly why merge sort, not quicksort, is the algorithm of choice on disk and tape: quicksort's random access would thrash.

**Q: What if duplicates should be removed rather than kept?**

A: Add a comparison against the last value you emitted and skip anything equal to it — a one-line change, still `O(m + n)`. The subtlety is that merging backward makes "last emitted" mean the value at `nums1[k + 1]`, and you must also handle duplicates *within* a single input array, not just across the two. Merging forward into a separate buffer is easier to get right here. Note the output length is then no longer `m + n`, so an in-place variant must also report the new length, the way Remove Duplicates (LC 26) does.

**Q: Your comparison uses `nums1[i] > nums2[j]`. Would `>=` change the result?**

A: Not the sorted output, but it does change which copy of an equal pair lands first, and therefore stability. With `>`, ties take the `else` branch and pull from `nums2`; with `>=`, ties pull from `nums1`. For plain integers the two outputs are identical and indistinguishable. It matters the moment elements carry payloads — records keyed by one field — because then "which equal record comes first" is observable. Merge sort's stability guarantee depends on consistently preferring the left-hand array on ties, so if you are merging backward and want a stable result, prefer the *later* array on ties to compensate for the reversed fill order.

## 15. Interview Explanation

> Since both arrays are sorted and `nums1` has extra space at the end, I merge from the back. I keep three pointers: one at the last valid element of `nums1`, one at the last element of `nums2`, and one at the last index of `nums1`. I compare the two largest available elements and place the larger one at the back. This avoids overwriting useful values in `nums1`. If any elements remain in `nums2`, I copy them. Remaining `nums1` elements are already in correct position. This gives `O(m+n)` time and `O(1)` extra space.

        k -= 1

    # Return the merged array for assertion checks
    return nums1
