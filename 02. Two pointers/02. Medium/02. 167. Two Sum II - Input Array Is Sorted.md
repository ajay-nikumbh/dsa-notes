# 167. Two Sum II - Input Array Is Sorted

| Difficulty | Pattern | LeetCode | Time | Space |
|:---:|:---:|:---:|:---:|:---:|
| **Medium** | Two Pointers | [167. Two Sum II - Input Array Is Sorted](https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/) | `O(n)` | `O(1)` |

## 1. Problem Statement

Given a **1-indexed** array of integers `numbers` that is already **sorted in non-decreasing order**, find two numbers such that they add up to a specific `target` number. Let these two numbers be `numbers[index1]` and `numbers[index2]` where `1 <= index1 < index2 <= numbers.length`.

Return the indices of the two numbers `index1` and `index2`, **each incremented by one**, as an integer array `[index1, index2]` of length 2.

The tests are generated such that there is **exactly one solution**. You **may not** use the same element twice.

Your solution must use only constant extra space.

### Examples

```text
Input:  numbers = [2,7,11,15], target = 9
Output: [1,2]
Explanation: The sum of 2 and 7 is 9. Therefore, index1 = 1, index2 = 2. We return [1, 2].
```

```text
Input:  numbers = [2,3,4], target = 6
Output: [1,3]
Explanation: The sum of 2 and 4 is 6. Therefore index1 = 1, index2 = 3. We return [1, 3].
```

```text
Input:  numbers = [-1,0], target = -1
Output: [1,2]
Explanation: The sum of -1 and 0 is -1. Therefore index1 = 1, index2 = 2. We return [1, 2].
```

### Constraints

- `2 <= numbers.length <= 3 * 10^4`
- `-1000 <= numbers[i] <= 1000`
- `numbers` is sorted in **non-decreasing order**.
- `-1000 <= target <= 1000`
- The tests are generated such that there is **exactly one solution**.

## 2. Core Theory

**The technique.** This is the purest form of the *converging two pointers on a sorted array* pattern. Start with `left` at the smallest value and `right` at the largest. The pair `(left, right)` gives you the extreme sum available in the current window, and comparing it against the target tells you unambiguously which end is useless and can be thrown away. Each iteration retires exactly one index, so the search finishes in at most `n - 1` steps: `O(n)` time, `O(1)` space.

**Why each move eliminates exactly one candidate without skipping an answer.** This is the argument to say out loud in an interview. Consider the live window `numbers[left..right]` and `total = numbers[left] + numbers[right]`:

```text
Case total < target:
    numbers[right] is the LARGEST value in the window.
    For every j in [left+1, right]:
        numbers[left] + numbers[j] <= numbers[left] + numbers[right]
                                    = total < target
    So numbers[left] is too small to reach target with ANY partner
    still in the window. Its only hope was the biggest partner, and
    even that fell short.
    => Discarding left destroys no solution. left += 1.

Case total > target:
    numbers[left] is the SMALLEST value in the window.
    For every j in [left, right-1]:
        numbers[j] + numbers[right] >= numbers[left] + numbers[right]
                                     = total > target
    So numbers[right] is too large to reach target with ANY partner
    still in the window.
    => Discarding right destroys no solution. right -= 1.
```

Formally, the loop invariant is: *if a valid pair exists anywhere in the array, it lies entirely inside `[left, right]`*. It holds at the start trivially, and the two cases above show each move preserves it. When `total == target` the invariant plus the current pair give the answer directly. If the pointers cross, the invariant says no pair existed at all.

**Why sortedness is load-bearing.** Both proofs lean entirely on "`numbers[right]` is the max of the window" and "`numbers[left]` is the min of the window". Remove sortedness and both statements are false, the elimination argument collapses, and the scan starts missing answers. That is why the unsorted variant (LeetCode 1) needs a hash map instead — and why this problem's `O(1)` space requirement is a hint, not a decoration: a hash map would cost `O(n)`.

**Recognising the pattern.**

| Signal | What it tells you |
|:---|:---|
| Input is stated to be sorted | The sortedness is the intended lever, not incidental |
| "constant extra space" required | Rules out a hash map, points at two pointers |
| Monotonic objective over a pair `(i, j)` | Moving one end changes the objective in a known direction |
| Exactly one solution guaranteed | You may return immediately on the first hit |
| 1-indexed output requested | Add 1 to both indices — an easy point to lose |

## 3. Problem Explanation

You are given a **1-indexed** sorted array `numbers`.

You are also given an integer `target`.

You need to find two numbers such that:

```text
numbers[index1] + numbers[index2] == target
```

Return their indexes as:

```text
[index1, index2]
```

Important points:

```text
Array is sorted in non-decreasing order.
Indexes are 1-based, not 0-based.
Exactly one solution exists.
You cannot use the same element twice.
```

### Example

```text
Input:
numbers = [2, 7, 11, 15]
target = 9

Output:
[1, 2]
```

Because:

```text
numbers[0] + numbers[1] = 2 + 7 = 9
```

But answer should be 1-indexed:

```text
[1, 2]
```

## 4. Core Intuition

This problem is different from normal Two Sum because the array is already **sorted**.

Sorted array means:

```text
Small values are on the left.
Large values are on the right.
```

So we can use two pointers:

```text
left  -> start of array
right -> end of array
```

Then check:

```text
current_sum = numbers[left] + numbers[right]
```

Now there are three cases:

```text
If current_sum == target:
    We found the answer.

If current_sum < target:
    Sum is too small, so we need a bigger number.
    Move left pointer forward.

If current_sum > target:
    Sum is too large, so we need a smaller number.
    Move right pointer backward.
```

This works only because the array is sorted.

## 5. Edge Cases

| Case | Input | Expected | Why it matters |
|:---|:---|:---:|:---|
| Minimum length array | `[1,2], target = 3` | `[1,2]` | `n == 2` is the smallest legal input; the loop must run exactly once. |
| Negative numbers | `[-1,0], target = -1` | `[1,2]` | Negatives are in the constraints; comparison logic must not assume positivity. |
| Both operands negative | `[-3,-1,0,2], target = -4` | `[1,2]` | Confirms `total < target` and `total > target` behave correctly below zero. |
| All identical elements | `[3,3], target = 6` | `[1,2]` | The two pointers land on equal values; must not reject them as "the same element". |
| Duplicates, answer uses one copy | `[1,2,2,3], target = 5` | `[2,4]` | Several index pairs sum to `5`; any valid one is accepted, but indices must be 1-based and distinct. |
| Duplicates not in the answer | `[0,0,3,4], target = 7` | `[3,4]` | The duplicate block must be walked past, not stalled on. |
| Answer at the extreme ends | `[1,2,3,4], target = 5` | `[1,4]` | Found on the very first comparison, before any pointer moves. |
| Answer in the middle | `[1,3,4,9], target = 7` | `[2,3]` | Requires moves from both sides before converging. |
| Zero target | `[-5,0,5], target = 0` | `[1,3]` | `target = 0` is legal; no special-casing needed. |
| Same element reuse forbidden | `[1,5], target = 2` | no solution | `1 + 1 = 2` must **not** be reported; `left < right` (not `<=`) enforces this. |
| Extremes of the value range | `[-1000,1000], target = 0` | `[1,2]` | Boundary values from the constraints. |

## 6. Brute Force Approach

### Idea

Try every pair of numbers and check if their sum equals the target.

### Example

```text
numbers = [2, 7, 11, 15]
target = 9
```

Check all pairs:

```text
2 + 7  = 9    found
2 + 11 = 13
2 + 15 = 17
7 + 11 = 18
...
```

Return:

```text
[1, 2]
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n^2)` | Because for every element, we check all elements after it. |
| **Space** | `O(1)` | Because we do not use any extra data structure. |

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def twoSum(self, numbers: List[int], target: int) -> List[int]:

        # Store the length of the array
        n = len(numbers)

        # Pick the first number using index i
        for i in range(n):

            # Pick the second number using index j after i
            for j in range(i + 1, n):

                # Check whether the selected pair forms the target sum
                if numbers[i] + numbers[j] == target:

                    # Return 1-based indexes as required by the problem
                    return [i + 1, j + 1]

        # This line is never reached because exactly one solution exists
        return []
```

## 7. Better Approach — Hash Map

### Idea

This is similar to normal Two Sum.

For every number, calculate:

```text
needed = target - current_number
```

Then check if this needed value was seen before.

### Example

```text
numbers = [2, 7, 11, 15]
target = 9
```

At index 0:

```text
current = 2
needed  = 7
```

7 not seen yet. Store:

```text
2 -> index 0
```

At index 1:

```text
current = 7
needed  = 2
```

2 already exists in hash map. Return:

```text
[1, 2]
```

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | We traverse the array once. |
| **Space** | `O(n)` | Because we store numbers in a hash map. |

### Code

```python
# Define the class solution
class Solution:

    # Define the method
    def twoSum(self, numbers: List[int], target: int) -> List[int]:

        # Create a dictionary to store number and its index
        seen = {}

        # Traverse every number with its index
        for index, num in enumerate(numbers):

            # Calculate the number needed to complete the target
            needed = target - num

            # Check if the needed number already exists in the dictionary
            if needed in seen:

                # Return the previous index and current index in 1-based format
                return [seen[needed] + 1, index + 1]

            # Store the current number with its index
            seen[num] = index

        # This line is never reached because exactly one solution exists
        return []
```

## 8. Why Hash Map Is Not the Best Here

Hash map gives good time complexity:

```text
O(n)
```

But it ignores the most important information:

```text
The array is sorted.
```

Because the array is sorted, we can solve it with:

```text
O(n) time
O(1) space
```

That is better than hash map.

## 9. Most Optimal Approach — Two Pointers

### Intuition

Place one pointer at the smallest number and one pointer at the largest number.

```text
left  = 0
right = len(numbers) - 1
```

Now calculate:

```text
current_sum = numbers[left] + numbers[right]
```

Because the array is sorted:

### Case 1: Sum is too small

```text
current_sum < target
```

This means we need a bigger sum. The only useful move is:

```text
left += 1
```

Because moving `right` backward would make the sum even smaller.

### Case 2: Sum is too large

```text
current_sum > target
```

This means we need a smaller sum. The only useful move is:

```text
right -= 1
```

Because moving `left` forward would make the sum even bigger.

### Case 3: Sum is equal to target

```text
current_sum == target
```

We found the answer. Return:

```text
[left + 1, right + 1]
```

Because the problem wants 1-based indexes.

## 10. Working Example

```text
numbers = [2, 7, 11, 15]
target = 9
```

Initial pointers:

```text
left  = 0 -> numbers[left]  = 2
right = 3 -> numbers[right] = 15
```

Current sum:

```text
2 + 15 = 17
```

17 is greater than 9. So we need a smaller sum. Move right pointer:

```text
right = 2 -> numbers[right] = 11
```

Current sum:

```text
2 + 11 = 13
```

13 is greater than 9. Move right pointer again:

```text
right = 1 -> numbers[right] = 7
```

Current sum:

```text
2 + 7 = 9
```

Found target. Return 1-based indexes:

```text
[left + 1, right + 1] = [1, 2]
```

## 12. Time and Space Complexity of Optimal Solution

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because each pointer moves at most n times. |
| **Space** | `O(1)` | Because we use only two variables: `left` and `right`. |

## 13. Optimal Code

```python
# Define the class solution
class Solution:

    # Define the method
    def twoSum(self, numbers: List[int], target: int) -> List[int]:

        # Initialize the left pointer at the start of the sorted array
        left = 0

        # Initialize the right pointer at the end of the sorted array
        right = len(numbers) - 1

        # Continue until the two pointers meet
        while left < right:

            # Calculate the sum of the numbers at both pointers
            current_sum = numbers[left] + numbers[right]

            # If the current sum is equal to target, we found the answer
            if current_sum == target:

                # Return 1-based indexes as required by the problem
                return [left + 1, right + 1]

            # If current sum is smaller than target, we need a bigger number
            elif current_sum < target:

                # Move left pointer forward to increase the sum
                left += 1

            # If current sum is greater than target, we need a smaller number
            else:

                # Move right pointer backward to decrease the sum
                right -= 1

        # This line is never reached because exactly one valid answer exists
        return []
```

## 14. Common Mistakes

| Mistake | Why it breaks | Fix |
|:---|:---|:---|
| Returning `[left, right]` instead of `[left + 1, right + 1]` | The problem is explicitly **1-indexed**; every answer is off by one. | Return `[left + 1, right + 1]`. This is the single most common wrong answer on this problem. |
| Writing `while left <= right` | Allows `left == right`, which reuses one element — `[1,5], target = 2` wrongly returns `[1,1]`. | Use `while left < right`, which enforces `index1 < index2`. |
| Moving the wrong pointer | Moving `right` down when the sum is already too small only makes it smaller, so the loop drifts away from the target and finds nothing. | Sum too small means you need a bigger value: `left += 1`. Sum too large: `right -= 1`. |
| Sorting the input first "to be safe" | The array is already sorted, and sorting a copy or in place either wastes `O(n log n)` or, if the input were unsorted, destroys the index mapping the answer depends on. | Trust the stated precondition and read indices directly. |
| Reaching for a hash map by reflex | Correct but `O(n)` space, and the problem explicitly demands constant extra space — it reads as missing the point of the question. | Use two pointers; mention the hash map only as the unsorted-input fallback. |
| Moving both pointers on a match | Harmless only because you return immediately, but if adapted to *count* pairs it drops answers. | Return on the match, or if counting, handle the equal-value block explicitly. |
| Overflow on `numbers[left] + numbers[right]` | Not an issue in Python, but in C++/Java with 32-bit ints near the limits the sum wraps and comparisons invert. | Use a 64-bit accumulator, or compare as `numbers[left] > target - numbers[right]`. |

## 16. Interview Follow-ups

**Q: What if the array were NOT sorted?**

A: The elimination argument dies, because `numbers[right]` is no longer the window maximum. Two options: sort first, which costs `O(n log n)` time and forces you to carry original indices alongside the values (`sorted(enumerate(nums), key=lambda p: p[1])`) since the problem returns positions; or use a hash map in a single pass, `O(n)` time and `O(n)` space, storing `value -> index` and looking up `target - num` as you go. If indices are required, the hash map is strictly better on time. If only the *values* are needed and space is tight, sorting in place plus two pointers wins on space.

**Q: What if the array is sorted but enormous — can you beat `O(n)`?**

A: Not in the worst case, since any correct algorithm must be able to inspect a linear number of positions. But you can improve the constant sharply with binary search: for each `left`, binary-search for `target - numbers[left]` in the suffix, giving `O(n log n)` — worse asymptotically, though better when the answer sits near the front. A genuinely useful variant is *galloping*: instead of `right -= 1`, binary-search for the largest index whose value is `<= target - numbers[left]`, which collapses long runs of oversized values in `O(log n)` and helps a lot on skewed data.

**Q: What if there could be zero solutions, or many, and you had to return all unique pairs?**

A: Drop the early return. On `total == target`, record the pair, then advance `left` past all values equal to `numbers[left]` and retreat `right` past all values equal to `numbers[right]` — the same adjacency trick 3Sum uses. That yields every unique *value* pair in `O(n)`. If you need every unique *index* pair, count the run lengths `a` and `b` and emit `a * b` pairs (or `C(a, 2)` when the two runs are the same block), which can be quadratic in output size.

**Q: How does this generalise to 3Sum and kSum?**

A: This is the base case of the whole family. Fix one index with an outer loop and run this exact scan on the rest, and you have 3Sum in `O(n^2)`. Fix two, and you have 4Sum in `O(n^3)`. In general `kSum` on a sorted array is `O(n^(k-1))`: peel indices with nested loops until two remain, then converge. The only addition at each level is skipping values equal to the previous one at that level, to keep the output free of duplicates.

**Q: Same setup, but find the pair whose sum is *closest* to the target.**

A: The scan is identical, but you never return early. Track `best` by `abs(total - target)`, update it every iteration, and move `left` when `total < target` and `right` when `total > target`. The elimination argument still holds for *exact* matches, and the running minimum catches the near misses along the way, so a single `O(n)` pass suffices. You can stop early only on an exact hit, since the distance is then zero.

**Q: What if the array were sorted in non-increasing order instead?**

A: Either reverse it conceptually by swapping the roles of the pointers — put `left` at the end and `right` at the start — or simply invert the two comparisons: when `total < target` you now move the *right* pointer, because the larger values live on the left. The safer answer in an interview is to state the invariant in terms of "the pointer standing on the smallest live value" and "the pointer standing on the largest live value", which makes the code direction-agnostic.

## 17. Interview Explanation

> Since the array is already sorted, I use two pointers: one at the start and one at the end. I compute the sum of both. If the sum equals the target, I return the two indexes incremented by one. If the sum is smaller than the target, I move the left pointer forward to increase the sum. If the sum is larger, I move the right pointer backward to decrease the sum. Sorting guarantees each move is the only useful direction, so this runs in `O(n)` time with `O(1)` space, which beats the hash map approach on space.

from typing import List


def two_sum_sorted(numbers: List[int], target: int) -> List[int]:
    left = 0
    right = len(numbers) - 1

    while left < right:
        current_sum = numbers[left] + numbers[right]

        if current_sum == target:
            return [left + 1, right + 1]
        elif current_sum < target:
            left += 1
        else:
            right -= 1

    return []
