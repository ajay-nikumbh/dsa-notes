# 11. Container With Most Water

| Difficulty | Pattern | LeetCode | Time | Space |
|:---:|:---:|:---:|:---:|:---:|
| **Medium** | Two Pointers | [11. Container With Most Water](https://leetcode.com/problems/container-with-most-water/) | `O(n)` | `O(1)` |

## 1. Problem Statement

You are given an integer array `height` of length `n`. There are `n` vertical lines drawn such that the two endpoints of the `i`th line are `(i, 0)` and `(i, height[i])`.

Find two lines that together with the x-axis form a container, such that the container contains the most water.

Return *the maximum amount of water a container can store*.

**Notice** that you may not slant the container.

### Examples

```text
Input:  height = [1,8,6,2,5,4,8,3,7]
Output: 49
Explanation: The above vertical lines are represented by array
[1,8,6,2,5,4,8,3,7]. In this case, the max area of water the
container can contain is 49.
```

```text
Input:  height = [1,1]
Output: 1
```

### Constraints

- `n == height.length`
- `2 <= n <= 10^5`
- `0 <= height[i] <= 10^4`

## 2. Core Theory

**The technique.** This is the *shrinking window with a dominance argument* flavour of two pointers. You start at the widest possible pair and move inward. Unlike Two Sum II, the array is **not sorted** and sorting would be useless — sorting destroys the x-coordinates that supply the width. What makes the scan valid is not order, but a *dominance* proof: at each step you can show that one of the two lines cannot appear in any better container than the one you just measured, so it may be retired permanently.

**The objective.** For indices `i < j` the area is `area(i, j) = (j - i) * min(height[i], height[j])`. Two forces pull against each other: moving inward always shrinks the width, so the only possible compensation is a larger `min`. That tension is the whole problem.

**Why discarding the shorter line is safe — the correctness proof.** Suppose `left < right` and, without loss of generality, `height[left] <= height[right]`. We have just recorded `area(left, right)`. Claim: **no pair that still uses index `left` can ever beat it.**

Take any `j` with `left < j < right` — that is, any remaining partner for `left`, all of which lie strictly inside the current window. Then:

```text
Width:
    j - left  <  right - left            (j is strictly nearer than right)

Height:
    min(height[left], height[j]) <= height[left]
                                  = min(height[left], height[right])
    (the last step uses our assumption height[left] <= height[right])

Therefore:
    area(left, j) = (j - left)      * min(height[left], height[j])
                  < (right - left)  * min(height[left], height[right])
                  = area(left, right)
```

Both factors are simultaneously no larger, and the width factor is *strictly* smaller. So every surviving pair involving `left` is strictly worse than the area already banked. Index `left` is dead, and removing it loses nothing. The key subtlety is the height bound: it does not matter how tall `height[j]` turns out to be, because the `min` is capped by `height[left]` regardless — the short line is the binding constraint against *every* possible partner.

**Why this makes the scan exhaustive.** Define the invariant: *the optimal pair is always contained within `[left, right]`*. It holds at the start, since the window is the whole array. Each step records `area(left, right)` and then discards an index proven not to belong to any unrecorded better pair, so the invariant survives. When the pointers meet, the window is empty and every candidate has either been measured or been proven dominated. Each step retires one index, so the scan is `O(n)` with `O(1)` space.

**On ties.** When `height[left] == height[right]` the proof above applies symmetrically to *both* lines, so either may be discarded — and in fact both can be. Moving just one (the usual `else: right -= 1`) is still correct, because the other will be handled on a later iteration.

**Recognising the pattern.**

| Signal | What it suggests |
|:---|:---|
| Maximise a quantity over a pair `(i, j)` where width matters | Start at the widest pair and shrink |
| The objective involves `min(a, b)` or `max(a, b)` of the two ends | The limiting end is the one you can prove dominated |
| Sorting would destroy information (positions, order) | Two pointers by *dominance*, not by order |
| Greedy shrink, and you must justify a discard | Write the two-factor argument: width strictly down, height capped |
| Contrast: Trapping Rain Water | Same `min` of two boundaries, but sums water per index rather than maximising one area |

## 3. Problem Explanation

You are given an integer array `height`.

Each element represents a vertical line:

```text
height[i] = height of line at index i
```

You need to choose **two lines** such that together with the x-axis they form a container that can store the **maximum amount of water**.

The water area between two lines is:

```text
area = width * minimum_height
```

Where:

```text
width          = right_index - left_index
minimum_height = min(height[left_index], height[right_index])
```

### Example

```text
Input:
height = [1,8,6,2,5,4,8,3,7]

Output:
49
```

Best pair:

```text
left index  = 1, height = 8
right index = 8, height = 7
```

Area:

```text
width  = 8 - 1 = 7
height = min(8, 7) = 7

area = 7 * 7 = 49
```

## 4. Core Intuition

Water stored between two lines depends on two things:

```text
1. Width between the two lines
2. Smaller height among the two lines
```

Important point:

```text
The shorter line decides the water level.
```

For example:

```text
height[left]  = 8
height[right] = 3
```

Even though left is tall, water can only go up to height 3. So:

```text
container height = min(8, 3) = 3
```

## 5. Edge Cases

| Case | Input | Expected | Why it matters |
|:---|:---|:---:|:---|
| Minimum length array | `[1,1]` | `1` | `n == 2` is the smallest legal input; the loop body runs exactly once. |
| All identical heights | `[5,5,5,5]` | `15` | The answer is purely the widest pair, `3 * 5`. Tests that ties do not stall the pointers. |
| Zero heights present | `[0,0]` | `0` | A container of zero height holds nothing; `max_water` must start at `0`, not at `-inf` or `None`. |
| Leading and trailing zeros | `[0,2,0]` | `0` | No pair has a positive `min`, so the answer really is `0` — not `2`. |
| Strictly increasing | `[1,2,3,4,5]` | `6` | Best is `(0,4)`? No — `(1,4)` gives `3*2=6` and `(0,4)` gives `4*1=4`. Confirms the widest pair is not automatically best. |
| Strictly decreasing | `[5,4,3,2,1]` | `6` | Mirror of the above; confirms the rule is symmetric. |
| Tall ends, short middle | `[9,1,1,1,9]` | `36` | The optimum is the widest pair; the shrink must not be tempted inward by the tall walls. |
| Short ends, tall middle | `[1,9,9,1]` | `9` | The optimum `(1,2)` is the *narrowest* interior pair; the scan must reach it. |
| Best pair is a single step apart | `[1,2,4,3]` | `4` | `(1,3)` gives `2*2=4`; `(2,3)` gives `1*3=3`. Tests the final iterations. |
| Single large spike | `[1,1,100]` | `2` | A tall line is worthless without a tall partner; `min` caps it at `1`. |
| Canonical example | `[1,8,6,2,5,4,8,3,7]` | `49` | The standard case, where the answer `(1,8)` is neither the widest nor the tallest pair. |
| Note on negatives | n/a | n/a | Constraints give `0 <= height[i]`, so negative heights cannot occur — a negative bar has no physical meaning here. Worth stating rather than silently assuming. |

## 6. Brute Force Approach

### Idea

Try every possible pair of lines.

For each pair:

```text
Calculate width
Calculate minimum height
Calculate area
Update maximum area
```

### Example

```text
height = [1,8,6,2,5,4,8,3,7]
```

Check pairs:

```text
(0,1), (0,2), (0,3), ...
(1,2), (1,3), (1,4), ...
...
```

For pair `(1,8)`:

```text
height[1] = 8
height[8] = 7

width = 8 - 1 = 7
min_height = 7

area = 49
```

This becomes the maximum.

### Complexity

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n^2)` | Because we check every pair. |
| **Space** | `O(1)` | Because we only store the maximum area. |

### Code

```python
# Import the required lib's
from typing import List

# Define the class solution
class Solution:
    def maxArea(self, height: List[int]) -> int:

        # Store the maximum water area found so far
        max_water = 0

        # Store the total number of vertical lines
        n = len(height)

        # Pick the first line using index i
        for i in range(n):

            # Pick the second line using index j after i
            for j in range(i + 1, n):

                # Calculate the width between both selected lines
                width = j - i

                # Calculate the smaller height because water is limited by shorter line
                min_height = min(height[i], height[j])

                # Calculate the water area for this pair
                current_area = width * min_height

                # Update maximum water area if current area is larger
                max_water = max(max_water, current_area)

        # Return the largest area found after checking all pairs
        return max_water
```

## 7. Better / Optimal Approach — Two Pointers

There is no separate meaningful "better but not optimal" approach here like hash map.

The main optimized solution is directly the **two pointers approach**.

## 8. Most Optimal Approach — Two Pointers

### Intuition

Start with the widest possible container:

```text
left  = 0
right = len(height) - 1
```

This gives the maximum possible width.

Now calculate the area. Then we need to move one pointer inward.

The question is:

```text
Should we move the taller line or the shorter line?
```

Answer:

```text
Move the shorter line.
```

### Why move the shorter line?

Suppose:

```text
height[left]  = 1
height[right] = 7
```

Water level is limited by:

```text
min(1, 7) = 1
```

If we move the taller line `right`, then width decreases and height is still limited by 1.

So area cannot improve.

But if we move the shorter line `left`, we may find a taller line that increases the limiting height.

That can potentially give a better area.

### Rule

```text
If height[left] < height[right]:
    move left pointer forward

Else:
    move right pointer backward
```

Because we always discard the shorter side.

## 9. Working Example

```text
height = [1,8,6,2,5,4,8,3,7]
```

Initial:

```text
left  = 0 -> height = 1
right = 8 -> height = 7
```

Area:

```text
width = 8
min_height = min(1, 7) = 1
area = 8 * 1 = 8

max_water = 8
```

Since left height is smaller, move left:

```text
left  = 1 -> height = 8
right = 8 -> height = 7
```

Area:

```text
width = 7
min_height = min(8, 7) = 7
area = 7 * 7 = 49

max_water = 49
```

Now right height is smaller, move right:

```text
left  = 1 -> height = 8
right = 7 -> height = 3
```

Area:

```text
width = 6
min_height = min(8, 3) = 3
area = 18

max_water = 49
```

Continue. No later area becomes bigger than 49.

Final answer:

```text
49
```

## 10. Time and Space Complexity of Optimal Solution

| Measure | Complexity | Why |
|:---|:---:|:---|
| **Time** | `O(n)` | Because each pointer moves at most n times. |
| **Space** | `O(1)` | Because we only use a few variables. |

## 11. Optimal Code

```python
# Import the required lib's
from typing import List

# Define the class solution
class Solution:

    # Define the method
    def maxArea(self, height: List[int]) -> int:

        # Initialize the left pointer at the first line
        left = 0

        # Initialize the right pointer at the last line
        right = len(height) - 1

        # Store the maximum water area found so far
        max_water = 0

        # Continue until both pointers meet
        while left < right:

            # Calculate the width between the current two lines
            width = right - left

            # Calculate the limiting height using the shorter line
            min_height = min(height[left], height[right])

            # Calculate current container area
            current_area = width * min_height

            # Update maximum area if current area is greater
            max_water = max(max_water, current_area)

            # If left line is shorter, move left pointer forward
            if height[left] < height[right]:

                # Move left inward to possibly find a taller line
                left += 1

            # Otherwise, right line is shorter or equal
            else:

                # Move right inward to possibly find a taller line
                right -= 1

        # Return the maximum water area found
        return max_water
```

## 12. Common Mistakes

| Mistake | Why it breaks | Fix |
|:---|:---|:---|
| Moving the **taller** line inward | Width strictly decreases while the height stays capped by the shorter line, so the area can only fall — and the genuinely better partner for the short line is never found. On `[1,8,6,2,5,4,8,3,7]` this returns `8` instead of `49`. | Always move the pointer standing on the shorter line: `if height[left] < height[right]: left += 1 else: right -= 1`. |
| Computing the area with `max` instead of `min` | Water is limited by the *shorter* wall; `max` overstates every container and yields an answer far too large. | `min_height = min(height[left], height[right])`. |
| Computing width as `right - left + 1` | This is an array-length formula, not a distance. The container's width is the gap between the two lines, so it over-counts by one on every pair. | `width = right - left`. |
| Starting `max_water` at `height[0]` or at the first computed area | On `[0,0]` an uninitialised or badly seeded maximum can return garbage; starting from a real area also breaks if the loop never runs. | Initialise `max_water = 0` — a legitimate lower bound, since areas are non-negative. |
| Using `while left <= right` | When `left == right` the width is `0`, so it adds a useless iteration, and in variants that index `left - 1` or `right + 1` it reads out of range. | `while left < right`. |
| Breaking early when the area drops | The area is **not** monotonic as the pointers converge — it dips and rises repeatedly (see the dry run, where `49` is followed by `18` then `40`). Stopping on a decrease misses later maxima. | Scan all the way until the pointers meet. |
| Sorting the array first | Sorting destroys the indices that define the width, so the computed areas correspond to no real pair of lines. | Never sort; the positions carry half the information. |
| On a tie, moving neither pointer | `if height[left] < height[right]` without an `else` branch, or an `elif` with no final case, leaves both pointers parked on equal heights and loops forever. | Make the `else` unconditional so every iteration moves exactly one pointer. |

## 14. Interview Follow-ups

**Q: What if you had to return the actual indices of the container walls, not just the area?**

A: Carry two extra variables alongside `max_water` and update them in the same branch that updates the maximum: `if current_area > max_water: max_water, best = current_area, (left, right)`. Cost stays `O(n)` time and `O(1)` space. One detail worth raising: use a strict `>` so you report the *first* optimal pair encountered, and ask the interviewer whether ties should return the widest, the leftmost, or all of them — on `[5,5,5,5]` several pairs tie at different widths, so "any optimal pair" and "the widest optimal pair" are different specifications.

**Q: Prove that moving the shorter line never skips the optimal answer.**

A: Suppose `height[left] <= height[right]` and the true optimum is some pair `(a, b)` with `left <= a < b <= right`. If `a != left` and `b != right`, the optimum is still inside the window after we discard `left`, so nothing is lost. If `a == left`, then `b` is some index in `(left, right]`. The case `b == right` is the pair we just measured and banked. For `b < right`, the two-factor argument applies: the width `b - left` is strictly less than `right - left`, and `min(height[left], height[b]) <= height[left] = min(height[left], height[right])`, so `area(left, b) < area(left, right)` and that pair cannot be optimal. Hence the optimum is either already recorded or still inside the shrunken window — which is exactly the loop invariant, and it holds until the pointers meet.

**Q: How is this different from Trapping Rain Water, which looks almost identical?**

A: Both use `min` of two boundaries, but the question differs. Container With Most Water asks for the single best *pair* — the bars in between are ignored entirely, and they cannot spill water because the container is a solid vessel. Trapping Rain Water sums water over *every index*, and the intervening bars both displace water and act as boundaries. Consequently Container maximises one area and tracks a running max; Trapping accumulates `min(left_max, right_max) - height[i]` per position. Container needs no auxiliary maxima; Trapping must track `left_max` and `right_max` as it goes.

**Q: What if the container could be slanted, or the lines had non-unit width?**

A: Slanting changes the geometry to a trapezoid, `area = width * (height[i] + height[j]) / 2`, and the dominance proof collapses — the taller line now contributes directly, so discarding the shorter one can throw away the optimum. You would fall back to `O(n^2)`, or to a convex-hull / rotating-calipers argument over the points `(i, height[i])`. Non-unit widths are gentler: if line `i` sits at x-coordinate `x[i]` with `x` increasing, replace `j - i` with `x[j] - x[i]` and the entire proof survives verbatim, because it only ever used "the nearer partner has strictly smaller width".

**Q: Can you find the *k* largest container areas?**

A: Not with the same scan, because the greedy discards pairs after proving only that they are worse than *one* recorded area — that is enough for the single maximum but not for a ranked list, since a discarded pair could still be second best. A correct approach keeps a size-`k` min-heap while enumerating candidates, which is `O(n^2 log k)` in general. If `k` is small you can prune hard: sort indices by height descending and stop expanding once the best achievable width times the current height falls below the heap's smallest element.

**Q: The heights arrive as a stream and you cannot store them all. What now?**

A: Two pointers need both ends at once, so the exact answer is out of reach in one forward pass with sublinear memory. What you *can* maintain cheaply is the set of candidates that could still be a left wall: a stack of strictly increasing-from-the-left record heights (every later bar shorter than an earlier record is dominated as a left wall by that record, which is both taller and further left). For each incoming bar, binary-search that stack for the best partner. Memory is the number of prefix records, which is `O(n)` worst case but typically `O(log n)` for random data.

## 15. Interview Explanation

> I will start with two pointers at both ends because this gives the maximum possible width. For every pair, I calculate the area using the smaller height because water level is limited by the shorter line. Then I move the pointer at the shorter line inward, because moving the taller line cannot improve the height limitation and only reduces width. This way, every move has a chance to find a better container. The time complexity is `O(n)`, and space complexity is `O(1)`.

### Key Interview Point

The most important logic is:

```text
Always move the shorter line.
```

Because:

```text
Area = width * min(left_height, right_height)
```

When width is decreasing, the only way to improve area is to find a taller minimum height.

from typing import List


def max_area(height: List[int]) -> int:
    # Initialize the left pointer at the first line
    left = 0

    # Initialize the right pointer at the last line
    right = len(height) - 1

    # Store the maximum water area found so far
    max_water = 0

    # Continue until both pointers meet
    while left < right:
        # Calculate the width between the current two lines
        width = right - left

        # Calculate the limiting height using the shorter line
        min_height = min(height[left], height[right])

        # Update maximum area if current area is greater
        max_water = max(max_water, width * min_height)

        # If left line is shorter, move left pointer forward
        if height[left] < height[right]:
            # Move left inward to possibly find a taller line
            left += 1
        # Otherwise, right line is shorter or equal
        else:
            # Move right inward to possibly find a taller line
            right -= 1

    # Return the maximum water area found
    return max_water


# Brute force reference, used to cross-check the greedy on every case
def max_area_brute(height: List[int]) -> int:
    # Store the maximum water area found so far
    best = 0

    # Store the total number of vertical lines
    n = len(height)

    # Pick the first line using index i
    for i in range(n):
        # Pick the second line using index j after i
        for j in range(i + 1, n):
            # Update maximum area using width times the smaller height
            best = max(best, (j - i) * min(height[i], height[j]))

    # Return the largest area found after checking all pairs
    return best
